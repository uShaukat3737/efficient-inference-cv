- why use torch.set_num_threads(1) for inference APIs?
  - by default, PyTorch attempts to use all available CPU cores per inference request.
  - under high concurrency (e.g. 20+ concurrent requests), this causes massive thread contention.
  - this thread explosion leads to severe CPU thrashing, causing the system to hang or drastically slow down.
  - setting threads to 1 forces parallelism to be handled safely at the API level (via async) and worker pool level (via multiprocessing) instead of PyTorch intra-op threading.

- why compare REST (FastAPI) vs gRPC?
  - REST uses JSON/Multipart over HTTP/1.1, which has massive textual parsing overhead and heavy network payloads.
  - gRPC uses Protobuf (binary serialization) over HTTP/2, drastically reducing payload size and serialization/deserialization CPU time.
  - evaluating both protocols side-by-side scientifically proves whether binary protocols (gRPC) yield higher throughput and lower latency for high-volume image inference compared to traditional web APIs.

--- Phase 4: REST vs gRPC Protocol Implementation ---

- why define image_data as raw bytes in the protobuf (not base64 string)?
  - REST multipart sends raw binary already; encoding it as a string would add base64 overhead (~33%) back in, defeating the purpose of gRPC.
  - protobuf bytes fields are natively binary — no encoding layer, no string parsing, minimal framing overhead.
  - this is the correct apples-to-apples comparison: raw binary in, raw binary out on both sides.

- why generate stubs into src/grpc_api/ instead of a top-level proto/ package?
  - stubs are tightly coupled to the server code that uses them — colocation inside the serving package makes imports predictable and avoids separate path configuration.
  - a top-level proto/ directory for stubs would require adding an extra sys.path entry or package install, increasing friction with no benefit.
  - the .proto definition stays in proto/ (source of truth), the generated python lives alongside what uses it.

- why use grpc.aio (async gRPC) instead of the synchronous grpc server?
  - the FastAPI server is async (ASGI); the comparison only holds if the gRPC server uses the same async concurrency model.
  - grpc.aio uses asyncio under the hood — the same event loop model — meaning both servers handle concurrent requests identically at the coroutine level.
  - a synchronous gRPC server would block on each poll loop iteration, artificially degrading gRPC latency and making the comparison meaningless.

- why reuse the same Producer class in the gRPC server instead of writing a new queue client?
  - the experiment goal is protocol comparison, not backend comparison. reusing Producer guarantees both servers go through the exact same Redis queue, batch scheduler, and worker pool.
  - any latency difference measured is purely protocol + serialization overhead, not backend variance.
  - diverging the backend would introduce a confound that invalidates the research result.

- why mirror the same POLL_ATTEMPTS=50 / POLL_INTERVAL=0.1 timeout as FastAPI?
  - both servers must have the same maximum wait budget (5 seconds) for a fair comparison.
  - if gRPC had a shorter timeout, it would appear to fail more under load; if longer, it would appear more reliable — neither would reflect protocol reality.

- why inject producer and redis_client into InferenceServicer via constructor arguments?
  - allows unit tests to inject mocks without patching module-level globals, which is fragile.
  - matches the same testability pattern used in the FastAPI server (mock_dependencies fixture).
  - makes the dependency graph explicit — the servicer does not own infrastructure, it receives it.

- why port 50051?
  - the IANA-registered default port for gRPC. using it means no configuration surprise for anyone running the stack.
  - keeps the system self-documenting: port 8000 = REST, port 50051 = gRPC.

- why measure payload size as part of the benchmark (not just latency/rps)?
  - latency and RPS alone cannot separate serialization cost from network cost from queuing cost.
  - payload size is the root cause of REST's overhead at scale: larger payloads = more bytes on the wire = more kernel buffer time = more TCP round-trip cost under high concurrency.
  - measuring it directly gives the thesis a concrete, citable number (e.g. "gRPC reduces payload by X% for CIFAR-10 sized images").

--- Research outlook for Phase 4 ---

- hypothesis: gRPC will show lower p99 latency than REST at high concurrency (c=50), even though both use the same backend queue.
  - reason: HTTP/2 multiplexing eliminates head-of-line blocking that HTTP/1.1 suffers under concurrent connections. at c=50, REST opens 50 separate TCP connections while gRPC multiplexes all 50 over one or a few connections, reducing OS socket overhead.

- hypothesis: the throughput gap between protocols will widen as concurrency increases.
  - at low concurrency (c=1), serialization cost dominates — gRPC wins slightly on parsing speed.
  - at high concurrency (c=50), connection overhead dominates — gRPC's HTTP/2 multiplexing provides a structural advantage REST cannot overcome without connection pooling.

- hypothesis: gRPC payload will be measurably smaller (~2-5 bytes of framing vs ~200 bytes of HTTP multipart boundary + headers), but the percentage difference shrinks as image size grows.
  - for tiny images (32x32), the overhead is proportionally large.
  - for real-world images (224x224), the fixed header overhead becomes a smaller fraction of total bytes — the relative advantage of gRPC narrows but absolute byte savings remain.

- open question: does HTTP/2 flow control introduce latency spikes at very high concurrency that are not present in HTTP/1.1?
  - HTTP/2 multiplexing is an advantage under moderate concurrency, but aggressive flow control backpressure on a single connection could create new bottlenecks at extreme load.
  - the p99 results at c=50 will surface this if it occurs.

- open question: does the async polling loop (50 × 0.1s) mask the true protocol latency advantage?
  - if the worker processes are the bottleneck (not the protocol), both servers will show similar p50 latency (worker-limited) and the protocol difference will only appear at the tail (p99) where connection overhead compounds.
  - this is worth noting in the thesis: the experiment measures end-to-end latency including queue wait, not raw protocol latency in isolation.

--- Phase 6: Docker Infrastructure ---

- why build Docker infrastructure if not testing Docker vs native on Apple Silicon?
  - Docker infrastructure (Dockerfile, docker-compose.yml, REDIS_HOST env var) is complete and tested — proves the system can be containerized and deployed in production.
  - on Apple Silicon (macOS), Docker runs Linux containers via VM; measuring Docker vs native would include VM overhead + CPU-only PyTorch, not representative of Apple hardware.
  - Docker benchmarks are deferred to NVIDIA Linux environments where Docker overhead can be fairly measured against native Linux performance on the same hardware.
  - Phase 6 provides production-ready Docker infrastructure; Phase 6 benchmarks use native Apple Silicon (MPS) as the baseline.
  - infrastructure-first approach: Docker is ready for cloud/CI deployment; benchmarks are optimized for local research measurement.

--- Phase 7: CPU vs MPS Hardware Acceleration ---

- why was Predictor hardcoded to CPU if training used MPS all along?
  - training (train.py) correctly auto-detects MPS via torch.backends.mps.is_available()
  - but Predictor was written without any device awareness — model.to(device) was never called
  - all inference benchmarks in phases 3–6 (latency, batch, throughput, worker scaling, gRPC) measured CPU inference only, even on Apple Silicon hardware
  - Phase 7 adds the device parameter to Predictor and benchmarks whether MPS changes the picture

- why default device="cpu" instead of auto-detecting MPS in Predictor?
  - the API and worker pool construct Predictor(path) without a device argument — auto-detection would silently change their runtime behavior
  - explicit parameter keeps the caller in control; benchmark scripts explicitly request "mps"
  - production serving stays on CPU unless intentionally configured otherwise

- why skip ONNX when device="mps"?
  - ONNX Runtime on macOS has no MPS execution provider
  - if device="mps" is passed for an ONNX model, the session silently falls back to CPU
  - benchmarking it as "mps" would label CPU results as MPS results — invalid comparison data
  - ONNX is skipped on MPS and only measured on CPU

- why wrap .to(device) in try/except with CPU fallback?
  - torch.jit.load(...).to("mps") raises RuntimeError on non-Apple-Silicon machines (Linux, CI)
  - the fallback ensures Predictor works on any platform without the caller needing to check hardware first
  - applies to both TorchScript (.pt) and raw PyTorch (.pth) branches

- why use torch.mps.synchronize() before stopping the timer?
  - MPS dispatches ops asynchronously — the kernel is queued, not executed, by the time Python returns
  - without synchronize(), time.perf_counter() captures dispatch overhead (~0.01ms), not actual inference (~6ms)
  - this would make MPS appear ~600x faster than CPU — a false result that would invalidate the benchmark
  - same requirement as torch.cuda.synchronize() for CUDA benchmarks

- why use time.perf_counter() instead of time.time() in the benchmark?
  - time.time() has ~1ms resolution on macOS, insufficient for measuring sub-millisecond operations
  - previous benchmarks (latency_test.py, batch_experiments.py) used time.time() — minor quality gap
  - perf_counter() uses the highest-resolution OS clock and is the correct choice for micro-benchmarks

- what the benchmark revealed:
  - MPS TorchScript at batch=64: 6,479 img/s vs CPU TorchScript 182 img/s (~35x throughput gain)
  - at batch=1: MPS (6.6ms) is 2x faster than CPU (13.7ms)
  - ONNX on CPU (0.55ms at batch=1) outperforms both MPS backends — ONNX's optimized runtime eliminates the MPS dispatch advantage for tiny batches
  - MPS benefit scales strongly with batch size: at batch=1 it is 2x; at batch=64 it is 35x
  - this supports the hypothesis that GPU acceleration pays off more as parallelism increases

--- Phase 8: Visualization Layer ---

- why a dedicated visualize.py instead of inline plotting in each benchmark script?
  - benchmark scripts are pure measurement; mixing plotting concerns in them would conflate "collect data" with "render data" and make re-rendering after a layout tweak require a full re-run
  - separating into visualize.py means plots can be regenerated for free from cached JSON results — every figure is reproducible without re-running expensive benchmarks
  - matches the broader system design: producer/consumer separation everywhere (data → queue → renderer)

- why pick the newest JSON per experiment automatically (latest_result)?
  - benchmark runs are timestamped; manually mapping experiment → result file would rot every time a new run lands
  - lexicographic sort over `<prefix>_*.json` works because filenames embed ISO timestamps (YYYYMMDD_HHMMSS) — chronological order falls out for free
  - new experiment runs are picked up automatically; no config update needed

- why one PNG per experiment instead of a multi-panel summary dashboard?
  - each figure answers exactly one research question — easy to drop individually into the thesis section that discusses it
  - dashboards force a fixed layout that fights LaTeX/markdown page templates and wastes ink for the questions a given section is not asking
  - rendering individual figures means a single chart can be regenerated without touching the others

- why exclude ONNX from the CPU vs MPS device comparison plots?
  - ONNX Runtime has no MPS execution provider on macOS — there is literally no MPS-ONNX line to draw
  - showing ONNX only on CPU side of a device comparison would imply asymmetric measurement and mislead at a glance
  - ONNX still appears on the format/batch comparison plots where CPU-only is the implicit baseline — the chart context tells the right story

- why log scale (base 2) on the batch-size axis?
  - benchmarks sweep batch sizes 1, 2, 4, 8, 16, 32, 64 — geometric progression
  - linear x-axis would compress small batch sizes into the left edge and make the ONNX/MPS curve shape unreadable
  - log2 spaces them evenly and reveals the diminishing-return point clearly

- why use matplotlib's "Agg" backend at import time?
  - the benchmarks run headlessly (CI, ssh, docker exec) — no display server
  - explicit Agg backend means the same code works on dev laptops and remote hosts without conditional setup
  - tests can import visualize.py without crashing when no display is available

- why was moving the __main__ block the only meaningful bug in implementation?
  - the test suite imports plot fns individually — by import time the whole module is loaded, so KeyError on globals() lookup never surfaces
  - end-to-end execution surfaces it on first run because __main__ runs *during* module load, before later defs are bound
  - lesson: always run the __main__ entry path as part of "done" verification, not just the tests
  - notes.txt logged it as a research observation — first-run failure is data

- what the visualizations exposed in real data that wasn't obvious from the JSON:
  - the worker-scaling chart shows throughput PEAKS at 4 workers and drops at 8 — context-switch tax dominates beyond the physical core count, even with multiprocessing
  - the device-latency chart has a visible non-monotonic kink at batch=16 on CPU; the JSON numbers alone made it look like noise
  - the gRPC vs REST p95 lines crossover at low concurrency in a way that the raw numbers obscured — visualization made the queue-dominated regime visible
