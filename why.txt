- why MobileNetV2 ?
  - less computationally heavy
  - good with :
    - pruning
    - quantization
    - batching experiments

- why TorchScript?
  -optimized version of PyTorch model
  -removes Python dependency
  -converts model into static graph
  -runs faster in production

- why put in evaluation mode?
  - disables:
    - dropout -> randomly drops neurons to prevent over-fitting -> dont rely on specific neurons -> forces the neural network to think on itself 
    - batchnorm updates -> we have evaluations already, having this on would mean using stats of the current batch which alone in itself is useless

- why batch processing?
  - memory efficient: 32 images at a time vs all 50k
  - scales to large datasets without OOM
  - production-ready pattern

- why take out LRU cache from model.py?
  - it was slowing down the model
  - it was not needed for the model

- why bisect module?
  - it is used to find the index of the batch that contains the given index
  - it is faster than iterating through the list

- why use torch.set_num_threads(1) for inference APIs?
  - by default, PyTorch attempts to use all available CPU cores per inference request.
  - under high concurrency (e.g. 20+ concurrent requests), this causes massive thread contention.
  - this thread explosion leads to severe CPU thrashing, causing the system to hang or drastically slow down.
  - setting threads to 1 forces parallelism to be handled safely at the API level (via async) and worker pool level (via multiprocessing) instead of PyTorch intra-op threading.
