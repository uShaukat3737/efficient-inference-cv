- why lazy load dataset instead of loading into memory?
  - on 8gb m1 unified memory, eagerly loading all 50k cifar-10 float32 tensors plus dataloader prefetch buffers pushed past physical ram limit
  - caused swap thrashing and mid-epoch oom kills (the dataset itself is ~600mb as float32, but combined with pytorch, model weights, and worker buffers it exceeded 8gb)
  - model training would fail mid-epoch requiring restarts
  - lazy loading with preprocessed batches and bisect module keeps resident footprint to ~200mb

- why use a strict latency timeout trigger in batch schedulers?
  - using blocking pop (brpop) caused workers to hang indefinitely under low traffic
  - api latency was unbounded, users waited indefinitely
  - non-blocking polling (rpop + time.sleep) with a 20ms timeout bounds maximum latency by forcing partial batch processing

- why disable pytorch intra-op parallelism (torch.set_num_threads(1))?
  - synchronous endpoints under high concurrency (20+) spawned 160+ active threads simultaneously
  - caused severe os context-switching overhead and cpu starvation (latency skyrocketed to 5000+ms)
  - disabling forces concurrency to be managed gracefully at the api and worker pool level

- why take out lru cache?
  - cache invalidation and memory indirection overhead slowed down tensor retrieval
  - benchmarking showed inference latency increased by 30-40%
  - the underlying bisect logic was already much faster

- why use a redis-backed queue instead of direct inference?
  - direct inference blocked the asgi event loop, limiting throughput to ~5 rps
  - decoupling via producer/consumer allows fastapi to instantly return while dedicated workers batch requests (1000+ rps)
  - correction: "~5 rps" for the sync endpoint was an estimate, not a measured result — no benchmark json records baseline sync throughput; actual value was never formally captured
  - correction: "1000+ rps" was a design goal, not a measured outcome — phase 8 worker scaling benchmark recorded actual peak of ~277 rps at 4 workers / concurrency=50 (fig_04)

- why fix batch size inconsistency?
  - caused shape mismatches and data loading failures during training
  - consistent sizes across training and inference prevent dimension mismatch errors

- why reorganize directory hierarchy?
  - initial structure scattered related code
  - modular structure (src/training, src/inference, src/serving, src/api) makes it highly maintainable

- why implement a model format fallback chain?
  - different formats have different performance characteristics (torchscript > onnx > pytorch)
  - robust fallback ensures the api always works with the fastest available format

- why implement image validation and error handling?
  - corrupted files or wrong formats caused cryptic server crashes
  - catching errors and returning http 400 with descriptive messages vastly improves api stability

- why add checkpoints per epoch?
  - long training runs could fail mid-training, losing all progress
  - checkpoints allow resuming from the last successful epoch

- why scale with a multiprocessing worker pool?
  - single-threaded inference bottlenecked concurrency
  - independent processes consuming from redis scale linearly (4 workers = ~200 rps)

- why compare rest vs grpc?
  - rest uses json/multipart over http/1.1 (heavy parsing, network payloads, base64 adds 33% overhead)

- Phase 6: Docker containerization and deployment
  - added Dockerfile with multi-stage build (builder + runtime stages)
  - used python:3.11-slim as base image to minimize container size
  - docker-compose.yml orchestrates three services: redis, worker, api
  - all services communicate via Docker Compose service discovery (hostname resolution)

  - grpc uses protobuf over http/2, reducing payload size and cpu time drastically
  - proves whether grpc optimizes ultra-high throughput scenarios (1000+ rps)

- why benchmark throughput vs latency trade-offs?
  - larger batches increase throughput but increase per-request latency
  - automated benchmarking finds the optimal operational balance

- why use a robust model export script?
  - exporting requires handling jit tracing, batch dimensions, and unsupported ops
  - validation ensures exported models produce identical output to the pytorch original

- why create test coverage for async components?
  - redis queues and background consumers are difficult to test natively
  - mocking (test_api) and fakeredis (test_queue) allows rapid testing without real servers

--- Phase 5: Metrics Collector Implementation ---

- why implement per-request metrics instrumentation?
  - existing benchmarks only measure end-to-end http latency externally
  - no visibility into latency breakdown: queue_wait vs batch_formation vs inference vs result_write
  - without instrumentation, impossible to diagnose performance bottlenecks (is p99 spike from queue saturation or inference?)
  - metrics feed all downstream experiments (protocol comparison, deployment env, hardware acceleration)

- why record enqueue_time in producer payload (not api)?
  - producer is the single chokepoint for all async requests
  - timestamp at push time is perfectly synchronized with actual queue arrival
  - distributes information naturally: api doesn't need to coordinate, workers see it directly

- why write metrics:{req_id} from worker instead of api?
  - worker sees true timing (dequeue, inference duration) that api cannot observe
  - worker is the authority on batch_size, batch_trigger (size vs timeout), inference_ms
  - separates concerns: worker owns inference metrics, api owns total_latency

- why use in-process metrics_collector instead of persistent store?
  - benchmarks run for minutes (1000+ requests), querying a database is expensive
  - in-memory rolling window (size=1000) provides fast percentile computation
  - research phase doesn't need durability; if process restarts, metrics reset

- why aggregate with percentiles (p50/p95/p99) instead of just mean?
  - mean latency hides tail behavior: mean=50ms but p99=500ms means users see inconsistent experience
  - p99 is the latency most users encounter under load; p95 shows typical behavior
  - reveals whether protocol/batching changes improve tail latency (research goal)

- all 19 tests pass on first implementation
  - strict tdd discipline (test red before implementing) prevented bugs
  - mocking strategy (metrics json from redis) made tests fast and deterministic
  - end-to-end smoke test (curl to /metrics) confirmed integration works

--- Phase 7: CPU vs Apple Metal (MPS) Benchmarking ---

- why add device parameter to Predictor?
  - training has always run on MPS (train.py uses torch.backends.mps.is_available())
  - but inference Predictor was hardcoded to CPU (no .to(device) calls anywhere)
  - all benchmark data collected so far (phases 3-6) measured CPU inference only
  - phase 7 answers: does MPS inference beat CPU for the same model and batch sizes?

- why default device="cpu" instead of auto-detecting MPS?
  - auto-detection would change behavior for all existing callers (api, worker pool, batch_experiments)
  - explicit parameter keeps callers in control; benchmark explicitly requests "mps"
  - production serving stays on cpu unless intentionally changed

- why skip ONNX on MPS?
  - ONNX Runtime has no MPS backend on macOS; session silently falls back to CPUExecutionProvider
  - benchmarking "onnx on mps" would measure cpu and label it mps — invalid comparison data

- why use torch.mps.synchronize() before stopping the timer?
  - MPS dispatches ops asynchronously (same model as CUDA)
  - without synchronize(), timer captures dispatch overhead (~0.01ms), not inference (~5-15ms)
  - would make MPS appear 100x faster than CPU — a false result

- why use time.perf_counter() instead of time.time()?
  - time.time() has ~1ms resolution on macOS, insufficient for sub-ms measurements
  - perf_counter() uses the highest-resolution clock on the platform

  - full suite: 35/35 passed, zero regressions across all prior phases

--- ONNX benchmark threading bug (discovered during Phase 9 analysis) ---

- onnx results were anomalously fast: 1.04ms vs 12ms for torchscript at batch=1 (~12x speedup)
  - observed: latency_test.py set torch.set_num_threads(1) for pytorch/torchscript but only set
    intra_op_num_threads=1 for onnx runtime; inter_op_num_threads was left at 0 (ort default = use all cores)
  - in predictor.py (used by batch_experiments.py), the onnxruntime session had no thread limits at all
  - pytorch/torchscript ran single-threaded while onnx runtime used all cpu cores for between-op parallelism
  - fix: set inter_op_num_threads=1 alongside intra_op_num_threads=1 in both latency_test.py and predictor.py
  - all 45 tests passed after fix; benchmarks re-run

- corrected results (latency_test): torchscript 11.7ms, pytorch 12.2ms, onnx 1.54ms
  - onnx gap narrowed from 12x to ~8x; remaining speedup is genuine
  - cause of genuine speedup:
    1. onnx runtime applies graph-level optimizations at session load (op fusion, weight pre-packing,
       constant folding) that pytorch does not apply at inference time
    2. on apple silicon, onnxruntime cpuexecutionprovider uses accelerate framework blas routines
       which are vectorized via neon; setting inter_op_num_threads=1 limits ort's own thread pool
       but does not prevent accelerate's internal vectorization
  - batch scaling for onnx is perfectly linear (~1ms/image, batch 1-64); torchscript shows
    expected sub-linear efficiency (overhead amortizes across batch) with a cache-spill kink at batch=16
  - conclusion: the corrected onnx numbers are valid research findings — the speedup reflects
    real format-level optimization, not a measurement artifact

- second round of fixes (same session): torch.no_grad() and time.perf_counter()
  - observed: latency_test.py called model(dummy_torch) directly without torch.no_grad() for
    both benchmark_torchscript() and benchmark_pytorch(); onnx has no autograd overhead at all
  - cause: pytorch builds an autograd graph even when inputs have requires_grad=False unless
    no_grad is explicitly set; this added overhead that onnx never pays → unfair penalty
  - fix: wrapped warmup and timed loops in torch.no_grad() in both functions
  - result: torchscript dropped from 11.7ms → 2.23ms; pytorch from 12.2ms → 2.74ms
    onnx unchanged at 1.04ms; gap narrowed from ~8x to ~2.5x
  - also replaced time.time() with time.perf_counter() in latency_test.py and
    batch_experiments.py for sub-ms precision (device_benchmark.py already used perf_counter)
  - also added torch.set_num_threads(1) to batch_experiments.py — onnx was thread-limited
    via predictor but pytorch/torchscript had no constraint (same imbalance, reversed direction)

- batch cliff at batch=16 under single-threaded constraints (discovered after above fixes)
  - with torch.set_num_threads(1) in batch_experiments.py, torchscript/pytorch show a dramatic
    latency spike at batch=16: torchscript 6.92ms (batch=8) → 327.5ms (batch=16), ~47x jump
  - onnx scales linearly throughout (~1ms/image at all batch sizes 1–64)
  - cause: pytorch eager execution does not pre-plan memory layout; at batch=16, intermediate
    activation tensors spill out of L2 cache on a single thread with no parallelism to hide it
  - onnx runtime pre-plans memory layout and op execution at session creation; cache-efficient
    single-threaded execution persists regardless of batch size
  - production implication: the batch scheduler fires at batch_size=8 or 20ms timeout;
    at batch=8, torchscript (6.92ms) is now faster than onnx (8.11ms) in single-thread mode
  - research implication: onnx's advantage is most pronounced at large batch sizes under
    single-threaded constraints — exactly the scenario where cache layout matters most
