==============================================================================
fix round 1 — 2026-04-26
issue: onnx inter_op_num_threads unrestricted
==============================================================================

files changed:
  benchmarks/latency_test.py    — added sess_options.inter_op_num_threads = 1
  src/inference/predictor.py    — added intra_op_num_threads=1 and inter_op_num_threads=1
                                   to onnxruntime SessionOptions

root cause:
  torch.set_num_threads(1) limits pytorch/torchscript to 1 thread.
  intra_op_num_threads=1 limits within-operator parallelism in ort.
  inter_op_num_threads was left at 0 (ort default = use all cores), allowing ort
  to parallelise between operators while pytorch ran fully single-threaded.
  predictor.py had no thread limits at all for onnx sessions.

==============================================================================
fix round 2 — 2026-04-26
issues: torch.no_grad() missing; time.time() instead of time.perf_counter();
        torch.set_num_threads(1) missing from batch_experiments.py
==============================================================================

files changed:
  benchmarks/latency_test.py    — wrapped warmup and timed loops in torch.no_grad() for
                                   benchmark_torchscript() and benchmark_pytorch();
                                   replaced time.time() with time.perf_counter() throughout
  benchmarks/batch_experiments.py — added torch.set_num_threads(1) at module level;
                                     replaced time.time() with time.perf_counter()

root cause (no_grad):
  pytorch builds an autograd graph every forward pass unless torch.no_grad() is set,
  even when input tensors have requires_grad=False. this overhead (graph node allocation,
  gradient bookkeeping) does not exist in torchscript or onnx. omitting no_grad unfairly
  penalised pytorch and torchscript vs onnx.
  predictor.py already used no_grad — latency_test.py was inconsistent with it.

root cause (time.time):
  time.time() has ~1ms resolution on macos, insufficient for sub-ms measurements.
  device_benchmark.py already used perf_counter; latency_test.py and batch_experiments.py
  did not. inconsistent clock resolution across benchmark scripts.

root cause (set_num_threads in batch_experiments):
  after round-1 fix, onnx sessions in predictor.py were thread-limited but pytorch/torchscript
  had no explicit constraint in batch_experiments.py — the imbalance was reversed.

note on batch>=16 cliff:
  with torch.set_num_threads(1) applied, torchscript and pytorch hit a sharp cliff at
  batch=16 (~47x jump from batch=8). onnx scales linearly throughout.
  cause: pytorch eager execution does not pre-plan memory layout; at batch=16 intermediate
  activations spill out of L2 cache with no parallelism to compensate.
  onnx runtime pre-plans memory layout at session creation; single-threaded execution
  remains cache-efficient at all batch sizes.
  production note: batch scheduler fires at batch_size=8 — within the efficient range.
  at batch=8, torchscript (6.92ms) is now faster than onnx (8.11ms) in single-thread mode.
